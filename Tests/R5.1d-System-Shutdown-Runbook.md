# R5.1.d — real Windows OS shutdown-delivery qualification

**Purpose:** prove that the Windows Service Control Manager delivers the actual system shutdown control to the generated service and that the service completes its own stop path before the guest OS shuts down.

This is a separate qualification from the direct HandlerEx callback probe in `Test-NativeScmServiceLifecycle.ps1`. Calling HandlerEx with value 5 proves only callback behavior. It is not an OS shutdown broadcast.

## Safety boundary

Run this only inside a disposable Windows Server 2025 VM with a recoverable checkpoint/snapshot and no production workloads. Do not run it on a developer workstation, shared runner, production host, or the GitHub-hosted CI runner. The test deliberately shuts down the guest OS. Keep the test service demand-start only.

The R5.1.d workflow does not initiate guest shutdown and must never execute this procedure as part of ordinary CI.

## Preconditions

1. The VM is isolated, booted, snapshotted, and can be restarted by its hypervisor.
2. The exact R5.1.d branch head and source tree SHA are recorded.
3. The VM uses the same Windows Server generation as the declared qualification target.
4. An administrator console and hypervisor-side control are available throughout.
5. The test service executable is generated by SharnouCompiler with:
   - `-EnableNativeScmServiceHost`
   - `-EnableNativeScmServiceTestMode`
   - `-NativeScmServiceTestFault None`
   - `-NativeScmServiceTestAction Service`
   - a unique disposable service name.
6. The test-only PE verifier accepts the image, the normal production verifier rejects it, and its SHA-256 is recorded.

## Procedure

1. Install the image as an own-process, demand-start service. Do not configure an automatic start type.
2. Start the service and capture repeated `sc.exe queryex <service>` output until `RUNNING` is observed. Verify:
   - process ID is nonzero;
   - checkpoint and wait hint are both zero;
   - the flags show STOP and SHUTDOWN acceptance;
   - the service name, executable path, source commit and executable SHA-256 match the test manifest.
3. Do not issue `sc.exe stop`, `ControlService(STOP)`, or any application-level stop request after this point. Record the no-STOP test interval in the controller log.
4. From the guest's administrator console, schedule a graceful OS shutdown with a delay long enough to collect evidence, for example:
   `shutdown.exe /s /t 45 /d p:4:1 /c "R5.1.d disposable OS shutdown qualification"`
   Do not pass `/f`; forced application termination would contaminate the evidence.
5. While the guest is shutting down, capture the service's SCM transitions and timestamps. The expected service-reported path is:
   - `SERVICE_RUNNING` with STOP and SHUTDOWN accepted;
   - `SERVICE_STOP_PENDING`, checkpoint 1, wait hint 5000 ms, controls accepted zero;
   - `SERVICE_STOPPED`, process ID zero, Win32 and service-specific exit codes zero.
6. Preserve the guest System event log covering the shutdown window and the controller/hypervisor log identifying the guest shutdown request and VM power-off. Correlate UTC timestamps. Verify the service reached its own STOPPED state before the guest completed shutdown and that no forced service-termination event occurred.
7. Restart the disposable VM from the hypervisor. Verify the service registration remains demand-start and STOPPED, PID zero, no service process is left running, and no deletion or test residue is present.
8. Export the complete `sc queryex` snapshots, guest System event log (EVTX plus rendered records), shutdown command result, hypervisor state transitions, source commit, executable hash, verifier output, and test operator notes into one evidence bundle. Hash every file and inspect the bundle after transfer.

## Pass criteria

All the following must be true:

- The VM shutdown was initiated by the OS shutdown path, not by an SCM STOP control or a user/application stop request.
- The generated service had advertised SHUTDOWN acceptance while RUNNING.
- The service published the expected STOP_PENDING fields, then STOPPED with PID zero and zero exit codes before guest shutdown completed.
- The event-log/hypervisor timeline is consistent with graceful service shutdown and contains no evidence that SCM forcibly terminated the service.
- The VM restarts successfully, the service registration is still present in demand-start/STOPPED state, and there is no orphan process.
- Evidence is bound to the exact tested commit and executable SHA-256 and is independently inspected.

Any missing transition, unexpected exit code, forced termination, ambiguous control source, or missing timestamp correlation is **INCONCLUSIVE/FAIL**, not a pass. Retain the VM snapshot and raw evidence for diagnosis.
